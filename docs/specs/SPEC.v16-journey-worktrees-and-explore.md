# SPEC.v16: Journey worktrees and explore commands

Participants open `develop/` and need two maps that the journey currently lacks: a short picture of which paths exist for this lesson, and a few shell commands that exercise what the lesson just taught (for example `list` after a list milestone). This outer harness spec adds both as labeled JOURNEY sections, keeps the worktree summary shallow so it stays readable, and binds explore-command curation to the lessons that actually introduce runnable behavior.

**Notation.** This file is an *outer* harness spec. Milestones are **outer.v16.M…**. Lesson ids match `workshop/JOURNEY.md` / `scripts/lesson-order` (e.g. `implement-2`, `quality-gates-3`).

**Section labels.** New journey markers use the same `*ALL CAPS*` style as `*PROMPT TO TEST*` / `*EXPECTED OBSERVATIONS*`:

- `*WORKTREE*` — autogenerated, at most two directory layers below the lesson root (files at the root may appear as leaves).
- `*EXPLORE COMMANDS*` — curated, optional per lesson; fenced shell commands a human can run in the prepared sandbox (or documented equivalent) to see the lesson’s behavior.

**Milestone ID note.** Explore milestones use lesson-bound ids (`M2-implement-1`, `M2-quality-gates-3`) after **outer.v16.M0** thawed `scripts/spec-check` to accept a hyphenated slug after the digits (alongside `M1` / `M2a`).

## M0: Lesson-bound milestone IDs in spec-check (Status: IMPLEMENTED)

Directors want outer milestones named after the lesson they serve (`M2-implement-1`), not only letter suffixes (`M2a`). The checker and the refine skill must agree on that shape before those headings are legal in every `docs/specs/SPEC.*.md`.

**Acceptance Criteria:**

- [x] `scripts/spec-check` accepts a flat milestone heading whose id is `M` + digits + one or more `-<slug>` segments where each slug starts with a letter or digit (examples: `M2-implement-1`, `M2-implement-1b`, `M2-quality-gates-3`), still accepts the existing `M1` / `M2a` forms, and still rejects ambiguous or empty postfixes.
- [x] `.claude/skills/refine/SKILL.md` documents the lesson-bound id form and that numbering stays local to each spec file; the fully-qualified reference remains `v<N>.M<id>` (e.g. `v16.M2-implement-1`).
- [x] In this file, the explore milestones are renamed from `M2implement-…` / `M2quality-gates-…` to the hyphenated `M2-implement-…` / `M2-quality-gates-…` forms in the same change that updates the checker, and `scripts/spec-check` exits 0 on this file afterward.
- [x] The test covers accept/reject fixtures for the new pattern and asserts the skill text and this file’s renamed headings. It does not start Claude.

**Implementation Details:**

- Python and Scala `HEADING` regex: letter postfix **or** one-or-more `-<slug>` groups. Tests: `tests/spec_check_test.py` + `tests/v16_journey_worktrees_test.py`.

## M1: Autogenerated `*WORKTREE*` sections for every journey lesson (Status: IMPLEMENTED)

Every lesson section in `workshop/JOURNEY.md` shows what a participant should expect under `develop/` for that lesson, without pasting a deep full-tree dump.

**Acceptance Criteria:**

- [x] A deterministic recipe or script (name pinned in Implementation Details) builds a **summary tree at most two layers deep** from the lesson’s prepared material root (default: `workshop/material/<lesson>/`, with a documented rule when the lesson’s material is a thin overlay on an earlier base).
- [x] Running that recipe inserts or refreshes a `*WORKTREE*` block in each lesson section of `workshop/JOURNEY.md` (placement fixed in Implementation Details: after the lesson’s link/meta lines and before `*PROMPT TO TEST*`). Regenerating is idempotent: a second run does not duplicate or drift the block when inputs are unchanged.
- [x] The tree omits build/cache noise (`target/`, `.bloop/`, `.metals/`, `.git/`, and any other paths listed in Implementation Details). Root-level files may appear; directories show at most their immediate children (no third layer).
- [x] Every lesson currently listed by `scripts/lesson-order` on `workshop/JOURNEY.md` has exactly one `*WORKTREE*` section after the recipe runs. The test compares a fixture journey + material tree to a golden summary and asserts the live journey has one worktree block per lesson. It does not start Claude.

**Implementation Details:**

- Script: `scripts/journey-worktrees`. Recipe: `just journey-worktrees`. Builds `00-base` + deltas through the lesson (same order as prepare). Skip dirs: `target`, `.bloop`, `.metals`, `.bsp`, `.git`, `.direnv`, `.claude-home`, `__pycache__`. Placement: immediately before `*PROMPT TO TEST*`.

## M2-quality-gates-1: Explore commands for quality-gates-1 (Status: IMPLEMENTED)

This is the easiest place to feel the pre-commit gate: a tiny staged change should refuse to commit while the suite is red, then succeed once green again.

**Acceptance Criteria:**

- [x] The `quality-gates-1` section has an `*EXPLORE COMMANDS*` block that walks a **fail-then-pass commit** path in the prepared sandbox: (1) break an existing test (or otherwise make `just check` fail), (2) `touch` a throwaway file (e.g. `test123`), `git add` it, and `git commit` so the pre-commit hook runs and the commit is rejected, (3) restore the test / make the check green, (4) commit again (or amend-free second commit) so the same kind of change succeeds.
- [x] The fenced block stays short (≤8 shell lines, including comments if any) and states cwd is the sandbox `develop/` (or equivalent). It names `git commit` and either `just check` or the hook; it does not require network.
- [x] The test asserts the block contains `touch`, `git add`, `git commit`, and a clear fail-then-pass intent (e.g. both a failing and a succeeding commit step, or comments that say expect fail / expect success). It does not start Claude.

**Implementation Details:**

- Documented break-a-test then `touch test123` / commit expect fail / restore / commit expect success.

## Non-goals

- Autogenerating `*EXPLORE COMMANDS*` from git history or LLM summary (curation stays human/director per lesson milestone).
- Deep trees, `target/` dumps, or full stamp TREE paste into JOURNEY.
- Changing product/develop SPECs inside the sandbox; this file only shapes the outer journey and harness checker.
- Adding explore blocks to early refine-only lessons in this version (can be a later outer.v16 follow-on if needed).
