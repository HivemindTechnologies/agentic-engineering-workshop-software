# Heading comparison

**Shared top-level concepts** (same role, though not always identical wording): Goals, Non-goals, Configuration, Store file/format, Commands/CLI surface, Output, Architecture, Dependencies (A only, see below), Testing strategy, CI, Milestones, Open questions for v2. Both also have an "Exit codes" subsection nested one level under the commands section.

**Where the outlines split:**

- Tree A (`01-03-25`) opens directly at `## 1. Goals`. Tree B (`01-05-14`) prepends a section A does not have at all: `## 1. Objective`, pushing everything else down one number.
- A has a standalone `## 8. Dependencies` section. B has no such heading — B folds suggested dependencies into prose inside `## 9. Architecture` instead.
- B has a standalone `## 8. Error handling` section with its own table. A has no equivalent heading — A's error behavior is scattered inside `### 4.1 Create-on-write, fail-on-read` and `### 5.1 Exit codes` instead of getting its own section.
- A structures commands as `## 5. Commands` (with `### 5.1 Exit codes` nested under it) and keeps `## 3. Configuration model` separate before it. B merges commands and the exit-code table into `## 4. CLI surface` (with `### Exit codes` nested under it), and puts `## 5. Configuration` *after* the CLI surface section rather than before it.
- A's output section is `## 6. Output` with subsections `### 6.1 `--format text`` and `### 6.2 `--format yaml``. B's output section is `## 7. Output rendering` with subsections titled `### Rich (default)` and `### YAML (\`--format yaml\`)` — different subsection labels (numbered vs. named, and "text" vs. "Rich" as the format name, which the body text confirms is a real naming divergence, not just a heading-label choice).
- B's CI section embeds a literal fenced code block whose first line is a YAML comment `# .github/workflows/ci.yml (sketch)`, which surfaces as its own heading-like line in the outline — a structural artifact A's `## 10. CI` section does not have.
- Numbering depth: A tops out at section 12 (`Open questions for v2`); B tops out at section 13, because of the extra `Objective` and `Error handling` sections.

This is not the same document with labels swapped — the section *count*, the *order* (Configuration before vs. after Commands), and the *presence/absence* of whole sections (Objective, Dependencies, Error handling) differ.

# Spec-text comparison

**Milestone order and size** — A ships in 8 milestones ending at CI wiring; B ships in 9, ending in docs/tag:
- A: "1. Project scaffold: `build.sbt`, dependency versions, empty `Main.scala` that prints usage; `just check` passes."
- B: "9. README usage docs + `--help` text polish; tag v1."

**Package names** — A uses a five-package layout under `todo/`; B uses a three-package layout:
- A: "domain/       Item, TodoList, pure operations (add, complete, uncomplete, remove, filter) — no IO, no Clock"
- B: "core/    — pure, effect-free: Task, TodoList, id assignment, status\n           transitions, YAML codec (encode/decode), rich-text rendering."

**How an item is identified** — A assigns ids by scanning/incrementing implicitly and stores no counter field; B stores an explicit counter:
- A: "`id` is a positive integer, assigned sequentially, never reused within a file ... Stored explicitly rather than implied by array position, so hand-edits that reorder lines don't change identity."
- B: "`nextId` is an explicit counter, not derived by scanning `tasks` for the max id. This keeps id assignment pure, deterministic, and independent of deletions."

**How errors are represented** — A defines four exit codes including a dedicated parse-failure code; B defines three, folding parse failures into a generic user-error code, and additionally specifies literal message text A never commits to verbatim:
- A: "| 3 | Store file exists but fails to parse (corrupt YAML, unknown `version`) |"
- B: "`` Error: no todo file at <path>. Run `todo add <title>` to create one, or pass --file <path>. `` Exit `1`."

**How color is applied** — different glyphs and different dimming target:
- A: "done items dimmed with a green marker; pending items with a yellow/plain marker; errors and warnings in red, always to stderr."
- B: "`✓` done rows render in green, `○` open rows in yellow, the id column dimmed."

**The rich-text/format grammar** — the two specs don't even agree on the flag's value name, which the outlines already hinted at (`--format text` vs `Rich (default)`):
- A: "`--format <text\|yaml>` | `text` | Output rendering for read commands (see §5)"
- B: "`--format` defaults to `rich`."

Additional corroborating divergence in the underlying data model (status representation and field naming), visible directly in the store-format quotes:
- A: `text: "Write the v1 spec"` / `done: true`
- B: `title: "Write the v1 spec"` / `status: done`

# Conclusion

The heading lists share a common skeleton (goals, non-goals, config, store, commands, output, architecture, testing, CI, milestones, open questions) but differ in section count, section order, and which topics get their own heading (Objective and Error handling exist only in B; Dependencies exists only in A). The body text confirms independent decisions at nearly every point checked: milestone count and final milestone differ, package layout differs (5 packages vs. 3), the id strategy differs (implicit sequential vs. explicit `nextId` counter), exit-code cardinality and meaning differ (4 codes vs. 3, with/without a parse-specific code), color glyphs and dimming targets differ, and even the format flag's accepted value differs (`text` vs `rich`). This is two independently authored specs pursuing the same brief, not one document with names changed.

verdict: pass
