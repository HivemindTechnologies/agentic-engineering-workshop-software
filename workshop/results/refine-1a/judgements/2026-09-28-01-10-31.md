### final reply

Nothing else in the repo constrains the design — this is a genuinely blank slate (no `build.sbt`, no `src`, no existing spec). Before drafting, I have a few ambiguities worth pinning down rather than guessing:

1. **File creation vs. "reads complain"** — I read this as: mutating commands that add a new todo (`add`, and an implicit `init`) create the store file if missing; every other command (`list`, and status-changing ones like `done`/`rm` that need an *existing* todo) must error clearly if the file is missing. Does that match your intent, or should *only* an explicit `init` ever create the file (i.e. `add` also errors on a missing file)?

2. **CLI command set for v1 MVP** — you didn't list commands. I'm planning to scope v1 to the smallest useful set: `init`, `add <text>`, `list`, `done <id>`, `rm <id>`. Is that the right cut for v1, or do you want something even smaller (e.g. no `done`/`rm` yet, just `init`/`add`/`list`)?

3. **File path** — default `./todo.yaml` in the cwd. Since config is CLI-args-only, is there a `--file <path>` flag to override that default, or is the path always exactly `./todo.yaml` with no override at all?

4. **"YAML and rich text directly"** — I read this as an output-format flag (e.g. `--format rich|yaml`, default `rich`), where `rich` is the colored/structured human view and `yaml` dumps the store's own YAML for scripting/piping. Does "interface directly" also mean YAML must be pipeable back in (e.g. `add` reading a YAML todo from stdin), or is YAML v1-scope read-only (output only)?

5. **Color in CI** — should color auto-disable when stdout isn't a TTY (so CI logs stay clean), plus an explicit `--no-color`/`--color` override? Or is a manual flag enough without auto-detection?

6. **Test framework** — CLAUDE.md fixes sbt + scalafmt + Cats Effect, but not a test library. Any preference (e.g. munit + munit-cats-effect, weaver), or should I just pick the simplest idiomatic option and state it as a criterion?

Once these are settled I'll draft `docs/specs/SPEC.v1-todo-list-cli-mvp.md` with flat milestones (project/CI scaffold, store model + YAML persistence, commands, colored/rich + yaml output) and checkable acceptance criteria, then stop for your review before any commit.
